# wa-blast · Standalone Refactor Design

**Date:** 2026-04-21
**Status:** Approved
**Author:** Luis + Claude

## Goal

Convert `wa-blast` from a Chatwoot-dependent UI layer into a **standalone WhatsApp marketing platform** that works next to any CRM (Chatwoot, Wati, Respond.io, custom, or none) via a webhook-proxy pattern.

Priorities: **scalability** (multi-tenant-ready from day 1) and **agility** (ship MVP fast, SQLite, no external services beyond Meta + Resend).

## Scope

**In scope (MVP):**
- Own auth system with Better Auth (email + password + email verification).
- Drop Chatwoot entirely — send via Meta Cloud API directly.
- Own contacts DB + tags + segments + CSV/Excel import.
- Webhook proxy: wa-blast is the sole Meta webhook subscriber, processes events, forwards raw payload to a configurable external URL.
- Single-tenant operation with schema prepared for multi-tenant (all domain tables carry `org_id`).
- Tables for campaigns + recipients + per-message events (analytics-ready).
- Auto opt-out detection via configurable keywords.

**Out of scope (MVP):**
- Scheduled sends (schema field exists, UI later).
- Carousel templates (separate feature).
- Inbound conversations / inbox UI.
- Billing, subscriptions, multi-tenant signup flow.
- Multi-channel (SMS, email).
- A/B testing.

## High-level architecture

```
Meta Cloud API
     ↑ send            ↓ webhook
     │                 │
┌────┴─────────────────┴──────────────────────────────────┐
│  wa-blast                                               │
│  ┌──────────┐  ┌──────────┐  ┌─────────────────────┐    │
│  │   Web    │  │  Sender  │  │  Webhook Proxy      │    │
│  │   UI     │  │  worker  │  │  (verify + forward) │    │
│  └────┬─────┘  └────┬─────┘  └──────────┬──────────┘    │
│       │             │                   │               │
│       └─────────────┴───────────────────┘               │
│                     │                                   │
│             ┌───────┴────────┐                          │
│             │  SQLite + BA   │                          │
│             │  (Drizzle ORM) │                          │
│             └────────────────┘                          │
└──────────────────────────────────────────────────┬──────┘
                                                   │ forward (optional)
                                                   ↓
                                           External CRM webhook
                                           (Chatwoot / Wati / etc)
```

Three internal services sharing one SQLite DB:

1. **Web UI** — Next.js App Router, auth-gated pages, server actions.
2. **Sender worker** — In-process background dispatcher, rate-limited, calls Meta Cloud API. Swappable interface for later replacement by BullMQ/Redis queue.
3. **Webhook proxy** — Single endpoint (`POST /api/webhook/meta`), processes events, forwards raw payload to external CRM in background.

## Auth & Tenancy

### Stack

- `better-auth` core + Drizzle adapter.
- `better-auth/plugins/organization` enabled from day 1 (inactive UI in single-tenant mode).
- `better-auth/plugins/next-cookies`.

### Tables (generated by Better Auth CLI)

`user`, `session`, `account`, `verification`, `organization`, `member`, `invitation`, `organization_role`.

### Roles per org

- `owner` — single per org. Can delete org, change billing (future).
- `admin` — invite/remove members, edit org settings and Meta creds.
- `member` — create campaigns, manage contacts/segments, view history. Cannot touch org settings or members.

### Signup flow (single-tenant)

1. User signs up with email + password at `/auth/signup`.
2. Better Auth sends verification email via Resend (`RESEND_API_KEY`).
3. On verify: if no org exists → create "default" org and assign user as `owner`. Otherwise user waits for invitation from an admin.
4. First-user-wins: the very first signup becomes owner of the default org.
5. After MVP stabilizes, a `DISABLE_SIGNUP` env toggle closes public signup and forces invitation-only.

### Protected routes

- Middleware `src/proxy.ts` checks Better Auth session cookie + active org membership.
- All `/app/*` routes require session.
- Active `organization_id` is read from session and used to scope every domain query automatically (enforced via a `scopedDb(orgId)` helper).

### Removed

- `iron-session`, `src/lib/session.ts` (manual), `src/app/login/actions.ts` (Chatwoot sign-in).

### Design notes

- `contacts.phone` is unique per org → safe upsert on import.
- `campaigns.scheduled_at` exists from day 1; MVP dispatcher only handles `scheduled_at IS NULL OR scheduled_at <= now()`.
- `message_events` kept separate from recipients so we can reconstruct funnels (sent → delivered → read → replied rates).
- `opt_out_at` on contacts filters them out of every segment automatically.
- Ad-hoc recipients (uploaded per campaign, not persisted to contacts) have `contact_id = NULL`.

## Sending pipeline

### Steps

1. User creates campaign in wizard: picks template → picks source (segment or ad-hoc CSV) → fills template params → preview → confirm.
2. Server action: transaction that creates `campaign` + N `campaign_recipients` rows. `status = 'queued'`.
3. Server action kicks `senderWorker.dispatch(campaignId)` (fire-and-forget promise tracked in-process).
4. Worker picks queued campaigns, sets `status = 'sending'`.
5. For each recipient, respecting `rate_limit_mps`:
   - Skip if `opt_out_at IS NOT NULL`.
   - `POST https://graph.facebook.com/v22.0/{meta_phone_id}/messages` with template payload.
   - Save `wamid` on recipient, update `campaign.sent`.
   - On error: classify (rate limit → backoff-retry, invalid number → mark failed, 24h window → mark failed). Save error string, increment `campaign.failed`.
6. When last recipient processed, set `campaign.status = 'done'`.
7. UI at `/historial/[id]` polls every 2s until status is terminal.

### Rate limiter

Simple token bucket per org, configured by `organization_settings.rate_limit_mps`. Default 20 msgs/sec (safe for Tier-1 Meta accounts). Can be raised per org.

### Swappability

The worker exposes a small interface:

```ts
interface SenderWorker {
  dispatch(campaignId: string): void;       // fire-and-forget
  status(campaignId: string): Promise<CampaignStatus>;
}
```

In-process implementation ships with MVP. A queue-backed implementation (BullMQ + Redis) can replace it without touching UI or actions.

## Webhook pipeline

### Endpoint

`POST /api/webhook/meta` — public route, no session required, Node.js runtime (for signature verification).
`GET  /api/webhook/meta` — Meta verification handshake (`hub.challenge` echo).

### Processing order

1. **Verify signature** — compute HMAC-SHA256 of raw body with `meta_app_secret` from matching org (matched by `metadata.phone_number_id` in payload), compare against `X-Hub-Signature-256`. Reject if mismatch.
2. **Identify org** — lookup `organization_settings.meta_phone_id = payload.phone_number_id`. If not found, 404 (without leaking info).
3. **Dispatch by event type:**
   - `messages.statuses[]` → for each: find recipient by `wamid`, write to `message_events`, update counters on campaign (`delivered`, `read`, `failed`).
   - `messages[]` (inbound):
     - Lowercase + trim body, check against `optout_keywords` → if match, set `contacts.opt_out_at = now()` by phone.
     - Find any recent recipient for this phone (last 7 days), increment `campaign.replied` if found.
     - Write event record (`event = 'replied'`, `payload = { phone, preview_truncated }` — never store full body).
4. **Forward** — if `forward_url` is set, enqueue background `fetch(forward_url, { method: 'POST', body: rawPayload, headers: { 'content-type': 'application/json', 'x-wa-blast-forward': '1' } })`. Retry 3x with exponential backoff (1s, 3s, 9s), 5s timeout each. Log failures. Never block response to Meta.
5. **Respond 200 to Meta** within ~100ms (all the above except forward is synchronous but fast).

### Forward semantics

- Payload is byte-for-byte identical to what Meta sent.
- The `X-Hub-Signature-256` header is **also forwarded** (still valid because payload is unchanged and the CRM holds the same app secret).
- The only added header is `X-Wa-Blast-Forward: 1` to make it traceable.

### Security

- Meta access tokens and app secrets are encrypted at rest in `organization_settings` using AES-256-GCM with a key from `ENCRYPTION_KEY` env var. Decrypted in-memory only when needed.

## Contacts + segments + import

### Import wizard

1. Upload CSV or Excel (.xlsx) using existing `xlsx` dep.
2. Detected columns shown with dropdowns: `phone` (required), `name`, `email`, + any N custom.
3. Phone validation with `libphonenumber-js` against org default country (setting in `organization_settings.default_country`, ISO-3166-1 alpha-2, default `"CO"`).
4. Dry-run preview: count of valid, invalid, duplicates (already in DB → will update), new.
5. On confirm: transactional upsert. `opt_out_at` is preserved on existing rows (never overwritten by import).

### Segments

Builder UI with condition groups:

```
Condition ::= { field: string, op: "eq"|"in"|"contains"|"exists", value: any }
Group     ::= { combinator: "AND"|"OR", conditions: [Condition|Group] }
```

Serialized to `segments.rule_json`. Compiled server-side to a Drizzle `where` clause. Always auto-filtered by `opt_out_at IS NULL`.

Preview: live count + first 10 contacts while building.

### Ad-hoc campaign upload

In the campaign wizard, user can choose "upload list for this campaign only". Same CSV upload, but rows go directly to `campaign_recipients` with `contact_id = NULL`. They are not persisted to `contacts`.

## Error handling (per layer)

- **UI:** All server actions return `{ ok: true, data } | { ok: false, error }`. `error.tsx` route boundaries catch unexpected throws.
- **Sender:** Classified errors per recipient (rate_limit, invalid_number, outside_24h, template_paused, auth_failed, unknown). Persistent in `campaign_recipients.error`. Auth failures mark campaign `failed` and alert via toast on next page load.
- **Webhook:** Never 5xx to Meta for business errors (Meta retries aggressively). Only signature-mismatch → 401. Unknown phone → 404. Internal failures logged but responded 200.
- **Forward:** Background, 3x retry, persistent failure logged but never affects Meta response.

## Testing strategy

- **Unit:** Segment query compiler, opt-out keyword matcher, rate-limiter, signature verification, encryption round-trip. Vitest.
- **Integration:** Drizzle migrations + seed, contact import happy/invalid/duplicate paths, campaign creation transaction. Vitest + in-memory SQLite.
- **E2E:** Sign up → verify email (mocked Resend) → create org → import contacts → create segment → create campaign → worker processes → mocked Meta receives messages → mocked webhook arrives → stats update. Playwright + MSW.

## Rollout plan

1. **Scaffold** — Drizzle schemas, migrations, Better Auth integration. App compiles but old routes broken.
2. **Auth + settings** — New login/signup/verify flows. Old Chatwoot login deleted. Settings page with Meta creds fields.
3. **Contacts + segments + import** — New CRUD + import wizard + segment builder.
4. **Campaigns rewrite** — New wizard, new sender worker, direct Meta send. Old history rewired to new tables.
5. **Webhook proxy** — New endpoint, signature verify, event processing, forward.
6. **Cleanup** — Remove all remaining Chatwoot code, env vars, docs.
7. **E2E test pass + first real-world campaign test.**

Each phase lands in its own PR/commit batch. No phase is mergeable until the app compiles end-to-end.
